# Выбор модели эмбеддингов (MEM-76)

Ноутбук `embeddings_check.ipynb` (собирается `make_notebook.py`) запускается в Colab на T4 и воспроизводится с нуля: скачивает и распознаёт ролики коллекции (faster-whisper large-v3), режет транскрипты на фрагменты, строит векторы двумя моделями, ищет по косинусной близости в памяти и считает метрики по контрольным запросам MEM-17. Результаты прогона 29.10.2026 — в `results/` (`comparison.csv`, `per_query.csv`, транскрипты 88 роликов).

**Условия:** 91 ролик (у 88 есть транскрипт; №30, 55, 56 не скачались — ищутся только по подписи), 107 запросов с ответом + 3 без ответа. Ролик ищется по всей коллекции; оценка ролика — лучший из его фрагментов; подпись — отдельный фрагмент.

## Выводы

1. Обе модели с запасом проходят цель Recall@10 ≥ 0,8 и обгоняют поиск по словам (0,77) на ~0,2.
2. **multilingual-e5-large лучше ставит правильный ролик наверх**: MRR 0,91 против 0,87, Recall@1 0,87 против 0,82. По Recall@10 модели равны (разница в 1 запрос).
3. **Окно 15 с / шаг 7 с** — лучшее на запросах Анастасии; весь транскрипт одним куском заметно хуже (MRR 0,83). Кроме того, e5 читает не больше 512 токенов — длинные куски обрезаются.
4. **Реранкер не берём:** прибавка +0,01 MRR, а на CPU он тратит ~40 с на запрос при требовании ≤ 2 с. Вернуться к нему можно только при сервере с GPU.
5. **Ограничение e5:** сходство у него сжато (топ-1 с ответом 0,85, без ответа 0,82), порог «ничего не найдено» по нему не поставить; у bge-m3 разрыв больше (0,61 против 0,49). Как отличать запросы без ответа — в MEM-41 (гибрид с BM25 или порог).
6. Цифры оптимистичны: коллекция маленькая (91 ролик), запросы писали люди, знающие ролики. На большой коллекции метрики будут ниже — финальный замер в MEM-55.

## MEM-80: полнотекстовый поиск PostgreSQL (базовая линия)

Лексический поиск средствами PostgreSQL: документ ролика — подпись паспорта и транскрипт целиком, `to_tsvector('russian', ...)` с GIN-индексом, запрос — ИЛИ русских лексем, ранжирование `ts_rank`. Замер: `MEM80_TEST_DSN=... python -m ml.lexical` (временная таблица в транзакции, данные БД не затрагиваются). Прогон 26.11.2026 на PostgreSQL 16.10 из `compose.yaml` (pgvector 0.8.0, `lc_ctype = en_US.utf8`).

| Метод | Recall@10 (hit@10) | macro Recall@10 | MRR |
|---|---|---|---|
| multilingual-e5-large, окно 15 с / шаг 7 с (MEM-76) | 0,963 | — | 0,912 |
| **PostgreSQL FTS, ролик целиком (MEM-80)** | **0,869** | **0,836** | **0,720** |
| BM25 по фрагментам, окно 15 с / шаг 7 с (MEM-76) | 0,766 | — | 0,650 |

107 контрольных запросов с ответом, 3 без ответа исключены; для 14 запросов правильных роликов несколько. Recall@10 здесь, как и в MEM-76, — доля запросов, где хотя бы один правильный ролик в первой десятке (hit@10; в JSON — поле `recall_at_10`); macro Recall@10 — средняя доля найденных правильных роликов, посчитана по сохранённым ранжированиям. Ранжирования и условия — в [`results/mem80_postgresql_baseline.json`](results/mem80_postgresql_baseline.json).

**Вывод.** Полнотекстовый поиск с русской морфологией лучше BM25 по фрагментам, но заметно уступает семантическому: MRR 0,72 против 0,91 — правильный ролик реже оказывается первым, а 2 запроса не находят ничего (перефразы без общих слов с роликом). Как базовая линия и кандидат для гибридного ранжирования (MEM-38/41) он годится: запросы, которые проваливает e5, нужно проверить по этим ранжированиям. Данные те же, что в MEM-76 (подписи паспорта 91 ролика и 88 транскриптов без очистки MEM-30), но FTS индексирует ролик целиком, а e5 — фрагменты, поэтому различаются не только методы поиска.

**Окружение влияет на результат.** Первый замер был сделан на PostgreSQL 18 под Windows с локалью `Russian_Russia.1251` и дал hit@10 0,776 и MRR 0,631 ([`results/mem80_postgresql_baseline_pg18_win1251.json`](results/mem80_postgresql_baseline_pg18_win1251.json)): при такой локали разбор русских слов в UTF-8 базе работает неверно, и 5 запросов (например, №1 «айтишник рассказывает про эксперимент») не находили ничего. Проверка регистра в `ml.lexical` при этом проходит, поэтому замер нужно делать на сервере проекта (`compose.yaml`, локаль UTF-8).

**Постоянный индекс.** Для работы приложения индекс строится модулем [`ml/lexical_persistent.py`](../../ml/lexical_persistent.py) по данным БД (`clips`, `transcript_segments`, фрагменты `ocr`/`scene`): `install` создаёт схему `mem80_lexical` с GIN-индексом, `index --collection UUID` атомарно перестраивает документы одной коллекции, `search` ищет в пределах коллекции. На локальной БД проиндексирована вся демонстрационная коллекция — см. [`ml/README.md`](../../ml/README.md).
