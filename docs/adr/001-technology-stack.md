# ADR-001: Выбор технологического стека

**Статус:** Принято  
**Дата:** 30.09.2026  
**Участники решения:** Вероника, Анастасия

## Контекст

MemSearch - интеллектуальная система семантического поиска и структурирования
пользовательского видеоконтента короткого формата.

Система должна обеспечивать загрузку и хранение видеоматериалов, обработку
видеоконтента с использованием методов машинного обучения, распознавание речи,
построение векторных представлений, семантический поиск, формирование кратких
описаний, тегирование и тематическую группировку видеоматериалов.

Часть операций обработки видеоконтента является вычислительно затратной и
может выполняться продолжительное время. Такие операции не должны выполняться
непосредственно в рамках пользовательского HTTP-запроса. При этом отдельные
ML-операции, необходимые для формирования ответа пользователю, например
построение векторного представления поискового запроса, должны выполняться
синхронно относительно пользовательского сценария.

Архитектура системы должна обеспечивать разделение пользовательского
интерфейса, серверной бизнес-логики, фоновой обработки и ML-компонентов.
ML-подсистема должна иметь возможность разрабатываться и контейнеризироваться
независимо от основной серверной части.

Команда проекта состоит из двух разработчиков, поэтому при выборе технологий
необходимо сохранить баланс между разделением ответственности компонентов,
возможностью дальнейшего развития системы и сложностью инфраструктуры.

## Решение

### Backend

Серверная часть системы реализуется на **Python** с использованием
**FastAPI**.

Для взаимодействия с базой данных используется **SQLAlchemy 2.x**. Доступ к
PostgreSQL из HTTP-слоя приложения выполняется асинхронно с использованием
`AsyncSession` и драйвера **asyncpg**.

Для управления схемой базы данных и выполнения миграций используется
**Alembic**.

Асинхронный подход применяется для I/O-операций серверной части. Длительные и
вычислительно затратные операции обработки видеоматериалов не выполняются
непосредственно внутри пользовательских HTTP-запросов и выносятся в фоновые
задачи.

### Хранение структурированных и векторных данных

В качестве основной системы управления базами данных используется
**PostgreSQL**.

PostgreSQL используется для хранения структурированных данных системы, в том
числе:

- данных пользователей;
- метаданных видеоматериалов;
- данных пользовательских коллекций;
- транскрипций;
- кратких описаний;
- тегов и тематической информации;
- состояний обработки видеоматериалов;
- ссылок на бинарные объекты.

Для хранения векторных представлений и выполнения семантического поиска
используется расширение **pgvector**.

Векторные представления хранятся совместно с предметными данными системы.
Такой подход позволяет выполнять реляционные и векторные запросы средствами
одной СУБД и не вводить отдельное специализированное векторное хранилище.

### Хранение бинарных данных

Исходные видеоматериалы и другие крупные бинарные артефакты обработки не
хранятся непосредственно в PostgreSQL.

Для хранения бинарных данных используется **S3-совместимое объектное
хранилище**.

В объектном хранилище могут размещаться:

- исходные видеоматериалы;
- извлечённые аудиофайлы при необходимости их сохранения;
- превью и отдельные кадры;
- другие бинарные результаты обработки.

В PostgreSQL сохраняются идентификаторы соответствующих объектов и связанные
с ними метаданные.

Использование S3-совместимого интерфейса предоставляет единый механизм доступа
к файлам для различных компонентов системы и позволяет не связывать
приложение с локальной файловой системой или конкретным облачным провайдером.

### Фоновая обработка

Для выполнения длительных фоновых операций используется **Celery**.

В качестве брокера сообщений для Celery используется **Redis**.

Celery worker является частью backend-подсистемы и отвечает за оркестрацию
длительных процессов обработки видеоматериалов. Backend ставит задачу
обработки в очередь и может завершить пользовательский HTTP-запрос, не ожидая
окончания обработки.

Celery worker получает задачу из очереди, обращается к ML-сервису и сохраняет
результаты выполнения в системе.

Состояние обработки видеоматериалов хранится в PostgreSQL и не зависит от
внутреннего состояния Celery. Это позволяет пользовательскому интерфейсу и
административным функциям получать актуальный статус обработки, отображать
ошибки и инициировать повторную обработку.

### ML-сервис

Функциональность машинного обучения выделяется в **отдельный
контейнеризованный сервис**, предоставляющий REST API.

ML-сервис отвечает за ML-операции, необходимые системе, в том числе:

- распознавание речи;
- построение векторных представлений;
- формирование кратких описаний;
- автоматическое тегирование;
- тематическую группировку.

Конкретные ML-модели и их параметры данным ADR не фиксируются. Они выбираются
отдельно на основании исследования и экспериментальной оценки.

ML-сервис не зависит от бизнес-модели backend, Celery и Redis. Взаимодействие
между backend-подсистемой и ML-сервисом осуществляется через явно
определённый REST API.

Для коротких операций, результат которых необходим непосредственно для
формирования ответа пользователю, backend может выполнять прямой асинхронный
HTTP-запрос к ML-сервису. Например, такой подход может использоваться для
получения векторного представления поискового запроса.

Длительная обработка видеоматериалов выполняется в фоновом режиме. Backend
создаёт Celery-задачу, а Celery worker оркестрирует процесс обработки и
обращается к REST API ML-сервиса.

Такое разделение позволяет независимо разрабатывать и контейнеризировать
backend и ML-подсистему, а также изолировать ML-зависимости от основной
серверной части приложения.

### Frontend

Пользовательский веб-интерфейс реализуется с использованием:

- **React**;
- **TypeScript**;
- **Vite**.

Для управления frontend-зависимостями используется **npm**.

TypeScript используется для статической типизации компонентов приложения и
структур данных, которыми frontend обменивается с backend.

Конкретная библиотека компонентов пользовательского интерфейса данным ADR не
фиксируется и может быть выбрана отдельно на этапе проектирования и реализации
интерфейса.

### Инструменты разработки

Для управления Python-зависимостями и виртуальным окружением используется
**uv**.

Для контроля качества backend-кода используются:

- **Ruff** — линтинг и форматирование Python-кода;
- **Pyright** — статическая проверка типов;
- **pytest** — автоматизированное тестирование.

Для frontend используются:

- **ESLint** — статический анализ TypeScript и React-кода;
- **Prettier** — форматирование;
- **Vitest** — автоматизированное тестирование.

Для выполнения быстрых локальных проверок перед созданием коммита
предусматривается использование **pre-commit**. Полный набор автоматических
проверок выполняется в CI.

### Контейнеризация и локальное окружение

Для контейнеризации компонентов системы используется **Docker**.

Для запуска и совместной работы компонентов в локальном окружении используется
**Docker Compose**.

Локальное окружение включает следующие логические сервисы:

- frontend;
- backend;
- Celery worker;
- ML-сервис;
- PostgreSQL с расширением pgvector;
- Redis;
- S3-совместимое объектное хранилище.

Backend и Celery worker используют один backend-код, но запускаются как
отдельные процессы и контейнеры.

Конфигурация компонентов передаётся через переменные окружения. Локальные
значения переменных окружения и секреты не сохраняются в Git. В репозитории
предусматривается файл `.env.example`, содержащий перечень необходимых
параметров без секретных значений.

### Непрерывная интеграция

Для организации непрерывной интеграции используется **GitHub Actions**.

CI запускается при создании и обновлении Pull Request в ветку `main`, а также
для изменений основной ветки.

Для backend предусматривается выполнение:

- Ruff;
- Pyright;
- pytest.

Для frontend предусматривается выполнение:

- ESLint;
- проверки форматирования Prettier;
- Vitest;
- проверки production-сборки.

После появления Dockerfile для компонентов системы в CI также должна
выполняться проверка успешной сборки контейнеров.

## Рассмотренные альтернативы

### SQLModel вместо SQLAlchemy

Рассматривалось использование SQLModel как более высокоуровневой абстракции,
ориентированной на совместную работу с FastAPI и Pydantic.

Выбран SQLAlchemy 2.x, поскольку он предоставляет более прямой контроль над
работой с PostgreSQL и сложными запросами и не вводит дополнительный слой
абстракции над SQLAlchemy.

### Синхронный доступ к PostgreSQL

Рассматривался синхронный доступ к PostgreSQL. Такой вариант является более
простым и достаточен для предполагаемой нагрузки системы.

Выбран асинхронный доступ, поскольку HTTP-слой приложения преимущественно
выполняет I/O-операции. Ожидание ответа базы данных при таком подходе не
требует блокировки потока обработки запроса.

При этом асинхронность не используется как способ выполнения
вычислительно затратных ML-операций. Такие операции выносятся в фоновые
процессы.

### Отдельная векторная база данных

Рассматривалось использование специализированной векторной базы данных для
хранения векторных представлений и выполнения семантического поиска.

Выбрано расширение pgvector, поскольку оно позволяет хранить векторные
представления совместно с предметными данными PostgreSQL и не требует
дополнительного инфраструктурного компонента.

Для предполагаемого масштаба MemSearch отдельная векторная СУБД не является
необходимой.

### Хранение бинарных данных в PostgreSQL

Рассматривалось хранение исходных видеоматериалов непосредственно в
PostgreSQL.

Данный вариант отклонён, поскольку крупные бинарные объекты существенно
увеличивают объём основной базы данных, при этом их содержимое не используется
в реляционных запросах.

### Локальное файловое хранилище

Рассматривалось хранение видео и других бинарных объектов в локальной файловой
системе с использованием Docker volume.

Такой вариант проще для первоначальной реализации, однако связывает
компоненты системы с конкретным файловым окружением и усложняет организацию
общего доступа к файлам из нескольких сервисов.

Выбрано S3-совместимое объектное хранилище, предоставляющее единый интерфейс
доступа к бинарным объектам.

### RQ вместо Celery

Рассматривалось использование RQ как более простого механизма фонового
выполнения задач на базе Redis.

Выбран Celery, поскольку обработка видеоматериалов является длительным и
потенциально многоэтапным процессом. Возможности повторного выполнения задач,
управления worker-процессами и дальнейшего разделения очередей лучше
соответствуют предполагаемому развитию системы.

### ML-код как часть backend

Рассматривалось непосредственное подключение ML-модулей к backend или Celery
worker в качестве Python-библиотеки.

Выбран отдельный ML-сервис с REST API. Это позволяет независимо разрабатывать
и контейнеризировать ML-подсистему, изолировать её зависимости от backend и
определить явный контракт взаимодействия между компонентами.

### Выполнение всех ML-операций через Celery

Рассматривалось выполнение любых обращений к ML-подсистеме исключительно
через очередь фоновых задач.

Данный вариант не выбран, поскольку некоторые ML-операции являются частью
интерактивного пользовательского сценария и требуют получения результата
непосредственно в рамках текущего HTTP-запроса.

Поэтому короткие ML-операции могут выполняться посредством прямого
асинхронного REST-вызова, а длительная обработка видеоматериалов выполняется
через Celery.

## Последствия

### Положительные

- backend и ML-подсистема могут разрабатываться и контейнеризироваться
  независимо;
- ML-зависимости изолированы от основной серверной части приложения;
- длительные операции обработки видеоматериалов не удерживают пользовательские
  HTTP-запросы;
- PostgreSQL используется одновременно для хранения предметных и векторных
  данных;
- отсутствует необходимость в отдельной векторной СУБД;
- бинарные данные отделены от основной базы данных;
- backend, Celery worker и ML-сервис могут масштабироваться независимо;
- S3-совместимое хранилище предоставляет общий механизм доступа к бинарным
  объектам;
- Docker Compose обеспечивает воспроизводимое локальное окружение;
- использование единых инструментов линтинга, форматирования, типизации и
  тестирования упрощает контроль качества кода;
- REST API формирует явную границу и контракт взаимодействия между backend и
  ML-подсистемой.

### Отрицательные

- по сравнению с монолитным приложением увеличивается количество
  инфраструктурных компонентов;
- необходимо поддерживать Redis, S3-совместимое хранилище и отдельный
  ML-сервис;
- необходимо разработать и поддерживать REST-контракт между backend и
  ML-сервисом;
- сетевое взаимодействие между backend и ML-сервисом создаёт дополнительную
  точку возможного отказа;
- необходимо обрабатывать таймауты и ошибки при обращении к ML-сервису;
- фоновые процессы требуют обработки ошибок, повторных запусков и контроля
  состояния;
- асинхронный доступ к базе данных увеличивает сложность backend-кода;
- локальное окружение требует больше вычислительных ресурсов из-за запуска
  нескольких контейнеров.

## Ограничения решения

Данный ADR фиксирует архитектурный и технологический фундамент проекта.

ADR не фиксирует:

- конкретные ML-модели и их параметры;
- конкретную UI-библиотеку;
- внутренние алгоритмы семантического поиска и ранжирования;
- конкретного поставщика S3-совместимого объектного хранилища;
- параметры развёртывания системы в production-среде.

Эти решения принимаются отдельно по результатам дальнейшего исследования,
экспериментальной оценки и реализации системы.
